# 1024×600、60 FPS 可行性与 v24 板端日志分析

评估基线：应用 v24 (`1415cce`)、D213 SDK `1a3fd0c`。目标更新为当前分辨率下
连续运动时稳定显示约 60 个不同画面/秒。v24 原先的 30 FPS 实验目标不再是最终目标。

结论：当前配置的显示时序允许 60 FPS，已有解码耗时也支持继续推进；但目前不能
承诺持续满帧。应用仍公告 30 FPS，本次日志甚至没有稳定收到 30 FPS，必须先查
视频输入节奏，再用 60 FPS 源验证硬解和显示并行后的持续能力。
本次是评估和日志定位，不修改固件行为，也不生成新的测试镜像。

## 硬件与配置依据

| 项目 | 源码/配置证据 | 对 60 FPS 的含义 |
| --- | --- | --- |
| CPU | SDK `.config` CPU 600 MHz | 解密、TCP/NCM、调度和码流处理共享 CPU，仍需满负载实测 |
| VE | `bsp/artinchip/hal/ve/aic_hal_ve.c` 的 `VE_CLOCK=200000000` | 当前设定值；单凭时钟不能换算解码 FPS |
| 面板 | LVDS、simple panel、match ID=0 | 实际选中 `panel_simple.c` 的 `timing_1024_600` |
| 时序 | pclk=52 MHz；横向 1024+160+160+20；纵向 600+12+20+2 | 理论刷新率 52e6/(1364×634)=60.131 Hz；实际时钟/VSYNC 频率仍需回板核实 |
| 协商 | `carplay_app.c:build_announcement_data()` 的 `info.max_fps=30U` | 需要公告 60 并验证手机实际出帧，不能只修改数值便宣称达标 |
| 显示路径 | MPP NV12 直接到 DE，无旋转 | 已省去整帧 GE 复制；应保留这一优势 |

SDK VE 文档列出 H.264 BP/MP/HP、Level 4.2、最大 1920×1088、80 Mbps；这是 SDK
通用能力描述，没有给出当前 D213/200 MHz/DDR 配置的持续 60 FPS 保证。
显示文档的 1080p60 能力也不能替代 H.264 解码吞吐测量。

1024×600@60 的有效像素吞吐是 36.864 Mpixel/s。以 16×16 宏块对齐为 1024×608，
每帧 2432 宏块，60 FPS 为 145920 宏块/秒。应从实际 SPS 核实 profile/level、参考帧
和编码尺寸，而不是只看接收器公告分辨率。

NV12 每帧有效图像为 921600 字节，60 FPS 解码写出约 55.3 MB/s，再加一次 DE
读取约为 110.6 MB/s。实际还包括步长/高度对齐、参考帧读写、UI 扫描、码流复制和
其他总线访问，不能把这个基础值当完整 DDR 带宽预算。USB 传输压缩 H.264；例如
平均每帧 20 KiB，60 FPS 对应约 1.23 MB/s、9.83 Mbit/s，实际应按运动场景测量
码率和突发，而不是将 NV12 原始带宽当作 USB 需求或用 USB2 理论 480 Mbit/s 作保证。

## 新 v24 日志已经证明什么

| 日志 | 可以得出的判断 |
| --- | --- |
| 第一窗 RX/show 都为 9.3；后续都在约 0.1–1.5 FPS | 这段运行里显示基本跟上已收到的视频，首先检查输入之前的链路 |
| queue=0/1、peak_total=2、drop=0、err=0 | 没有解码队列持续积压或压缩输入丢失的证据；不能用扩队列解释修复 |
| decode 7–15 ms，present 6–13 ms | 当前低帧率下的视频工作耗时；还不能代表满 60 FPS 的尾延迟和争用 |
| process 0.6–14 ms，assembly 55 ms–6.343 s | 大部分时间发生在收到首段头部至整条消息完成之间，而不是消息处理回调 |
| sender_gap 约 53 ms–1.475 s | 收到的视频时间戳间距也很大；可能是内容变化少或源端受背压，不能单独判为手机主动限帧 |
| KiB/s=15–61 | 当前观察到的完成读取速率；不是 USB 链路最大可用吞吐 |

assembly 从首次收到消息头开始计时，包含等待后续字节、owner 调度和任务抢占，
不包含消息开始前的纯空闲，也不是隔离的 CPU/解密时间。接收和 sender gap 的窗口
样本不完全相同，不能机械相减计算端到端延迟。没有连续运动条件说明，不能用这些
窗证明源端本来只能输出低帧率。

### USBMUX 异常优先级较高

手机连续报告 `detected duplicate packet. Expected 110 received 111...118`，表明
接收端的序号预期持续停在 110。报文文字叫 duplicate，并不证明应用真的重复发送了
同一个序号：显示出来的收到序号是逐步增加的。

已对照 usbmuxd `3ded00c` 的 `src/device.c`：当前 mux tx 序号递增、回显对端 rx_seq
规则与参考一致。不能因为警告而直接改回显字段或把计数器强行改成 110。

当前 `core/usb/usbmux_host.c:send_tcp()` 在 transport.send 之前递增 tx_index；
`handle_tcp()` 的若干自动 ACK 发送忽略返回错误。这使一次发送失败后继续输出后续
序号成为可能，但本日志没有该次失败的底层返回值，也可能涉及传输/设备侧接收。
需要记录首个失败/异常时的 mux 序号、TCP flags、端口、帧长、USB 实际长度和返回值，
再决定失败时关闭并重建会话。不能在不知道是否部分发送成功时盲目重传 TLS 字节。

USBMUX 承载 carkit/iAP2，Screen 走 IPHETH 上的 IPv6 TCP；两者共享 USB 控制器，
但不是同一逻辑流。控制流异常应修复，尚不能将它认定为 Screen 慢的唯一原因。

### 控制命令有了具体类型

此前未知的 `/command` 现明确包括 `modesChanged` 和 `disableBluetooth`，仍返回405；
`/feedback` 也返回405。应按命令语义补齐模式状态和能力处理，并与开源实现对照。
日志没有证明这些405必然导致当前低帧率，也不应把所有未知命令一律回复200。

## 通往稳定 60 FPS 的顺序

1. **先定位输入停顿和 USBMUX 序号缺口。** 补齐首错诊断/传播，测 Screen body 分片
   到达间隔、owner 最大服务间隔、IPHETH 完成至重挂间隔；必要时抓包看 TCP 窗口/
   重传。v24 批量读取本身没有证明消除了这段停顿，不再重复基础 ping/枚举测试。
2. **建立 60 FPS 输入实验。** 公告60，检查 SPS 和时间戳，在持续运动内容中验证
   sender/RX 是否接近60。源端不提供60个画面时，接收器重复扫描无法补成60个不同画面。
3. **解码与显示并行。** 每帧预算16.667 ms；历史 decode≈8 ms、present≈8 ms 的
   串行路径余量很小，而且 decode 统计按非空调用，不一定每帧只有一次。vsync等待是
   wall time，不能直接等同 CPU 成本，也不能相加两个最大值推断极限。将 VE 和 DE
   分为两个 worker，保留直接 NV12、扫描帧引用及 stop/reset 生命周期屏障，并验证
   MPP 缓冲和锁的并发契约。这是 Zalink 接入层最值得借鉴的部分。
4. **按实际占用优化接收/复制。** 若解码与显示已留余量，仍因 owner/CPU 跟不上，再
   引入独立 Screen owner、复用输入存储和减少复制。不能先靠提高全体优先级或无限
   扩队列追 FPS；参考链丢失仍须 IDR 恢复。

Zalink 的配置 fps=0 注释为默认60、解码/显示分线程，是可行性线索；其闭源协议库、
无线和关闭音频的运行条件、没有本板60FPS记录，都限制了它作为性能证明的用途。
UxPlay/DiPlay 的异步接收、输出线程提供结构参考，同样不能证明 D213 能跑满60。

## 建议验收口径

* 在源端确实持续更新的场景中，至少连续60秒，sender/RX/成功显示的独立画面速率
  接近59–60 FPS，并记录5秒窗口和逐帧间隔，避免仅用长时间平均数掩盖停顿。
* 压缩输入无丢失、无解码错误、队列不持续增长；统计成功 DE 更新及 VSYNC，不能
  把当前即使 layer ioctl 失败也会增加的 frame_count 当作严格显示成功计数。
* 记录 p95/p99 帧间隔和队列龄期，明确长帧次数；保留触摸和控制响应，并在目标音频
  场景下复测。平均60FPS不等同触摸延迟合格。
* 本地同规格 H.264 60 FPS 码流单独验证 VE→DE，完整有线链路验证网络/解密→VE→DE。
  前者能区分硬解上限与输入链路问题，不能替代后者验收。

当前判断是“有条件可行，值得按上述顺序优化”，不是“硬件已经证明稳定60”。
