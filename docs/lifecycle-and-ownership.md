# Lifecycle and ownership

## Owner thread

Every Receiver instance has one host-selected owner. Create, start, poll, state query, stop and destroy run there. The host serializes UI, touch, radio and USB requests before they enter the protocol. Receiver does not create detached workers. A state callback can copy/query state but cannot reenter lifecycle operations. Never destroy a Receiver from a media callback. A callback that needs shutdown posts a host request and returns.

## Owned and borrowed resources

Create copies the public platform/media/iAP2 descriptors and initial capability document. Pairing strings, accessory identifiers/public keys, OS/network tables, callback contexts and any provider storage remain borrowed. Keep them valid and immutable until destruction. The optional compatibility converter copies the same descriptors without taking ownership. Start owns the RTSP listener and, as negotiated, control, timing, event, Screen, iAP2 and audio endpoints. Those endpoints own their protocol buffers and cryptographic state. Existing persistence providers retain ownership of pairing files; stopping a receiver does not delete bond/trust records.

Screen Annex-B buffers and decrypted/encoded audio buffers are borrowed until their callbacks return. Asynchronous sinks must copy or complete an explicitly supported ownership transfer before returning. A state callback's pointer is also borrowed. `rtcp_receiver_get_state()` copies values, so a host can publish that copy under its own synchronization. It must not pass a live Receiver pointer to unsynchronized UI queries.

## Shutdown and failure

Stop runs on the protocol owner, closes all endpoints and completes their synchronous teardown callbacks before returning. A host-owned media worker must finish consuming copied buffers before its device/context is freed. Stop does not join a host-created worker; the host must request exit and join/acknowledge it before destroy. On failed start, the object remains stopped and retryable. Repeated start and stop are idempotent. Generation increases only after successful start.

## Transitional RT-Thread composition

`application/rt-thread/rtcarplay/app/carplay_app.c` still wraps Receiver with a legacy singleton, poll worker, touch queue and board initialization. Its lifecycle and diagnostic APIs predate the portable owner-thread contract. Wireless/wired endpoint queries now copy strings into caller storage; each iAP2 link retains its own endpoint copy for callback and identity pointers. Only the source-version constant remains static SDK data. The LVGL launcher and Connection Manager are now owned by Luban-Lite. The host now separately tests callback/worker retirement and copied diagnostics against the actual composition and adapters. Portable Runtime tests alone do not establish board scheduling or device behavior.

The wrapper now serializes lifecycle entry with a nonblocking atomic gate: simultaneous or reentrant start/stop returns `RTCP_ESTATE`. Stop from the poll worker also returns `RTCP_ESTATE` instead of joining itself. Worker ownership is published before scheduling; failed thread creation/startup rolls back resources. Atomic completion flags live outside resettable session storage, and teardown no longer clears the singleton before the worker's final state access. A successful stop therefore waits even when the worker had not yet been scheduled. Bluetooth owner claim/release uses compare-and-exchange so the launcher and shell cannot both acquire the transport. The CarPlay Control shell now queues requests for the poll owner and reads copied status; it never operates the Browser itself. USB and wireless iAP2 workers serialize commands and retain provider/endpoint ownership through timeout and late cleanup. Touch, audio output, video and microphone workers have separate retirement regressions.

The wrapper no longer stores a raw RTSP server pointer. Peer and media/timing diagnostics use copied public Receiver snapshots on the poll owner. The `carplay_ab` command shares the lifecycle gate and queue mutex, publishes requested framing and reports the applied/pending values; only the poll worker calls the Receiver setter. Pending requests disappear on stop/restart, preserving default chunked framing. The legacy PIN pointer getter is restricted to the serialized lifecycle owner. Cross-thread consumers use the copied display/PIN query. Audio output and video reject self-join, retire accepted readers before deletion and retain resources after stop timeout; microphone stop retains its borrowed network context until the worker acknowledges exit. The application shutdown owner retries failed retirement before releasing its dependencies.

Copied metadata and debug queries use a shared reader count outside resettable session storage. They coexist with other readers and input, while lifecycle operations block new queries and sleep until active readers return before destroying/resetting resources. Shell status shares lifecycle exclusion and reads queue counters under the queue mutex. HID counters and encrypted-event readiness are atomic. Pairing storage publishes its actual write result separately, so query contention cannot masquerade as persistence failure. Link endpoint refresh commits only on success; a failed refresh does not invalidate pointers already retained by iAP2. See the host [snapshot contract](https://github.com/boa-z/luban-lite-carplay/blob/carplay-oss/application/rt-thread/rtcarplay/docs/session-snapshots.md).

## Regression evidence

Touch and Siri enqueue operations use the same nonblocking gate as start/stop. A request returns `RTCP_ESTATE` during lifecycle/input contention without reading the session mutex; stop retains the gate until that mutex has been destroyed. The worker clears its thread handle before publishing completion, so an exited worker's handle cannot be mistaken for a later caller. Callers must handle a rejected enqueue according to their input policy; the API does not promise delivery during shutdown.

The Host lifecycle regression checks reentrant destroy rejection, copied configuration, retry after listener failure and repeated teardown with a connected client. The encrypted end-to-end regression checks authentication, separate endpoint readiness and reconnect. These tests do not validate RT-Thread scheduling, hardware device close, DMA lifetime, USB host cancellation or physical reconnect; each requires its corresponding adapter/hardware procedure.

`test_rtthread_app` additionally compiles the actual RT-Thread composition with the real Linux network/entropy ports and protocol implementation, modeling only RT-Thread scheduling and mutexes. It checks creation/startup failure rollback, rejected lifecycle reentry, input/lifecycle exclusion during enqueue and mutex destruction, self-stop rejection, 32 start/immediate-stop/retry cycles before first scheduling, and two pthread contenders claiming Bluetooth ownership over 64 rounds. It now runs in the Luban-Lite host `make -C application/rt-thread/rtcarplay check`, together with the relocated board regressions. This is Host scheduling-model evidence, not a real RT-Thread board run.
