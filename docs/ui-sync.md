# UI Sync protocol foundation

The optional rtcp/ui_sync.h processor implements the bounded UI Sync message/state foundation reviewed in LIVI ui_sync.rs at revision 64a05b68358db52ed887169143afd5944fd6f1f7. Based on LIVI by Lasse Heitgres (https://github.com/f-io/LIVI); see NOTICE. This processor does not provide theme assets, an OpenGL renderer, a frame compositor, presentation synchronization, official authorization or qualification. It does not advertise uiSyncInfo or enabledFeatures. The D213 application does not attach it yet.

## Host composition

Create a processor with an actual Main Display UUID, select a layout supplied by the host's theme inventory and optionally set dark mode. Configuration, layout, palette and component identifiers are copied. Set rtcp_receiver_config_t.ui_sync to the borrowed processor, retain it until Receiver destruction and attach it to only one Receiver. All Receiver and processor calls belong to the same serialized owner. NULL keeps the Classic path and allocates no UI Sync model workspace. The SDK remains independent of LVGL, MPP, DE and D213.

Attachment registers the UI Sync Type 130 UUID, while still requiring Pair-Verify, encrypted control, successful initial SETUP and the phone's uiSync feature offer. It rejects overlapping raw UI registration. Vehicle State processors or raw vehicle backends can coexist. Registration and a working state machine alone are insufficient to declare a renderer or theme inventory to a real phone; capability composition is a separate gate.

allow_layout_change is an explicit host policy, returned to the phone as a boolean. give_focus is disabled by default. Enable it only with the host's actual focus_token, bounded to INT64_MAX. The reference's constant 4711 is not assumed to be a universal protocol token. Layout/appearance requests and recorded phone choices do not themselves render or present any pixels.

## Wire and state

A complete decrypted body is an OPACK dictionary containing displayUUID and binary data. That data is a binary plist header with type, ssn, psn and asn; command data is another binary plist. The display UUID must match the configured display. Other bounded OPACK panel metadata is retained and echoed, rather than discarded when constructing responses. Duplicate matching routing fields are rejected in both envelope and plist lookups. Existing Classic plist lookup behavior remains unchanged; plist type queries now correctly distinguish boolean markers from null.

Reset increments the local session, resets transmit/receive/acknowledgement sequences, captures an optional scalar phone id and answers with version 2. A repeated reset while waiting for completion is ignored. Reset-complete for the active session negotiates version 1 or 2, answers with reset-complete, emits allow-layout-change, requests a selected layout if present and optionally gives focus. Version 0 is refused. Version 1 omits the captured id from reset-complete. The id may be an ASCII string of at most 255 bytes, data of at most 256 bytes, integer, boolean or null; complex and non-ASCII id forms are explicitly unsupported.

Ready commands update recorded layout, palette and appearance choices using the reference's start-layout-transition (0x03), palette-change (0x10) and appearance-preference (0x13) forms. Request-focus (0x08) may generate give-focus (0x07) when the host opted in. Commands generate application ACK unless noAck is true. Unknown command kinds are counted and acknowledged without invented behavior. Stale sessions are ignored; already-seen command sequence numbers are acknowledged without applying choices again. ACK headers track the peer's receive sequence and acknowledgement of generated messages; an acknowledgement beyond the last generated transmit number is refused. Sequences are bounded to INT64_MAX and wrap is refused.

Requested layouts use request-layout (0x05), explicit light/dark appearance, fadeInNewLayout/fadeOutOldLayout and the supplied activeComponents map. The host can observe desired layout and phone choices separately with rtcp_ui_sync_status. An ACK confirms neither actual renderer acceptance nor presentation time. There is no inferred timeout, retransmission window, theme authenticity check or frame-clock protocol in this foundation. Real-phone compatibility with sequence/duplicate policies remains NOT_RUN.

## Output ownership and limits

One model keeps at most four pre-encoded messages of 8192 bytes each. Reset-complete may need all four slots. rtcp_ui_sync_peek borrows the oldest encoded output; rtcp_ui_sync_consume releases it only after the transport copied it. Another input or host selection while output is pending returns ESTATE before processing. Encoding and parsing failures leave protocol state and output uncommitted, while rejection/receive counters remain observable. The instance uses bounded heap storage for model state, staged state, nodes and output; the message path has no per-request heap tree or full-message stack array.

Receiver polling retries pending messages when a queue is full. If another request arrives while retained output still cannot queue, Receiver rejects it before applying choices and retires only the UI lane. Channel close, authentication loss and Receiver start/stop reset the UI handshake, phone choices and pending output; desired layout/dark mode and cumulative counters survive. A fresh channel must reset/negotiate again. Status counts generated, consumed and abandoned messages, and the Receiver delivery query counts copied messages, queue retries, rejected inputs and the last local error. Direct raw sends to an attached UI lane return ESTATE. Enqueue/consume is not proof of phone receipt.

Identifiers are nonempty ASCII strings of at most 64 bytes, and a layout has at most eight distinct active zones. Panel metadata has at most 1024 encoded bytes. The internal nested-plist writer accepts at most 128 preorder nodes, depth 16 and 16384 output bytes, supporting null/boolean/integer/ASCII string/data/array/dictionary values. Dictionary keys must be strings. It rejects unsupported real/date/UUID/non-ASCII nodes and malformed trees; extended collection lengths and negative eight-byte integers are supported. These are explicit foundation limits, not claims about the full official protocol.

## Installed host inventory

Before negotiating a UI channel, a host may bind `rtcp_ui_sync_inventory_t` through `rtcp_ui_sync_bind_inventory()`. The inventory identifies one theme, panel and matching display, nonzero pixel/physical dimensions, and supported layouts with per-layout palettes and allowed zone/component pairs. Binding copies all identifiers and nested arrays into optional bounded heap storage; caller buffers can be released afterward. `rtcp_ui_sync_get_inventory()` returns a borrowed read-only view, valid until successful rebind/unbind/destruction. An unbound model retains the existing protocol-foundation behavior and allocates no inventory storage.

The bound is eight layouts, eight palettes per layout and sixteen alternative zone/component pairs per layout. Inventory identifiers are printable nonempty ASCII strings of at most 64 bytes. Duplicate layouts, duplicate palette IDs within a layout and duplicate exact component pairs are refused. Multiple components for one zone are allowed alternatives. Selecting a component from the wrong zone is unsupported; there is no Cartesian product of all declared zones/components. A desired layout can still activate a subset of at most eight distinct zones.

Binding or unbinding requires IDLE and no retained output. A replacement must support any existing desired layout, palette and active components. Failure preserves the old inventory, desired layout and output. With an inventory bound, host selection and phone layout/palette choices outside it return ENOTSUP before state or ACK output is committed. An inventory survives channel/session reset with the desired layout. An unsupported authenticated request follows the Receiver's existing application-refusal policy: retire the UI lane, preserve other lanes and require a fresh handshake. Real-phone behavior for that policy is NOT_RUN.

Receiver delivery status now retains `last_rejection` alongside the rejected-request count. It preserves the exact application/delivery refusal when a subsequent generic channel-close error replaces `last_error`. Queue exhaustion and unsupported inventory choices can therefore be distinguished after lane retirement. The last rejection persists across resets until another request is rejected or the Receiver is destroyed.

This inventory is a host implementation contract, not a theme parser, authenticity verifier, renderer or presentation callback. Binding it does not emit displayPanels/uiSyncInfo or enable uiSync. Synthetic test identifiers must not be presented as an implemented vehicle theme. Capability composition still requires the host's actual rendering/theme inventory and completed handlers; the D213 profiles do not bind or advertise this protocol yet. The [additional LIVI theme review](livi-theme-review.md) explains why the reference's metadata tests do not establish complete official Local UI rendering.

## Validation and remaining acceptance

tests/check_ui_sync_wire.py generates checked-in synthetic input bytes using Python plistlib and independently decodes outgoing OPACK/plist messages. The initial scenario follows LIVI's public synthetic reset/layout test, using a distinct configurable focus token. Tests cover version 1/2, layout/component/dark requests, phone layout/palette/appearance choices, focus policy, application ACK/noAck, stale/duplicate messages, future ACK rejection, retained output, reset preservation, scalar id forms, duplicate routing fields, non-ASCII/complex id refusal, oversized panel metadata, truncations and a deterministic malformed-input corpus. Plist writer tests cover null/bool/signed/data/extended arrays, every output-capacity truncation, invalid trees and depth limits. Python also validates the outgoing wire independently of the SDK parser.

The encrypted Receiver scenario combines actual Vehicle State and UI Sync application processors over real Host TCP/Pair-Verify/ControlCipher. It checks the four-message negotiation, exact transport sync token, application ACK/noAck, a blocked socket filling seven transport slots and retaining the eighth response, rejection of the ninth request before applying its layout, fresh-seed reopen, bad-tag isolation, a surviving vehicle read and subsequent Classic audio/video regression. It leaves an unconnected UI listener for authenticated session destruction to clean up. These are simulated-controller Host tests, not L3/L4 real-iPhone evidence.

The complete official Ultra goal still requires gated /info capability composition, actual theme/display inventory and rendering, graphics/HEVC/wireless integration, presentation timing, real-phone negotiation and vehicle/UI interaction, and the applicable official integration and qualification process. See [the overall foundation and L0–L5 scope](ultra-foundation.md).

Inventory unit tests cover copied nested ownership, invalid identifiers/dimensions/counts/duplicates, matching-display binding, atomic replacement, exact zone/component alternatives, per-layout palettes, rejected local selection, independently encoded unsupported phone choices, no committed state/ACK on rejection and reset retention. The encrypted Receiver scenario binds synthetic inventory, rejects an authenticated unknown layout on only the UI lane, preserves the exact last_rejection, continues Vehicle State reads, then accepts supported layout/palette choices on a fresh UI channel. Python independently decodes 35 outgoing messages. SDK Make, CMake 65/65 and the complete integration Host suite passed with this milestone on 2026-11-15; none is real-phone or renderer evidence.
