# CarPlay Ultra protocol foundation

The intended product goal is complete official CarPlay Ultra. The current foundation provides portable display metadata, OPACK and bounded Vehicle State/UI Sync processors with optional Receiver composition. It does not establish Ultra negotiation, official qualification or a working Ultra renderer. Classic video with local instruments is a separate integration result. No new Ultra capability is advertised by these APIs automatically.

They are not a public substitute for all protocol, authorization and product requirements. Source compatibility with LIVI alone does not prove official Ultra support.

## Display and OPACK APIs

The public display profile carries one Main Display UUID, view area, safe area and appearance metadata. A null profile preserves Classic metadata. Both rectangles must fit inside their parent; an omitted rectangle uses the parent area. A profile does not add Type 111, altScreen, HEVC, displayPanels, Vehicle State or UI Sync. The shared integer aspect-fit and inverse touch-map helpers reject touches in letterbox bars.

OPACK uses caller-owned preorder tokens, validates UTF-8, finite numbers, references, nesting, complete containers and trailing bytes, and supports scalar, array and dictionary values. Limits are 512 tokens, depth 16 and 65,536 encoded bytes. Signed transaction identifiers are preserved. Duplicate routing keys are ambiguous and cannot be looked up. Encoding has no object-reference compression. Unknown tags and unsupported references are rejected.

## Vehicle State model

The host explicitly supplies accessory, service and characteristic IID/type values, ownership, mutability, units, optional numeric range/step and initial values. The SDK includes no guessed vehicle catalogue. The current bound is eight characteristics and 256 bytes per string/data value. Boolean, integer, floating, UTF-8 string and binary data values are supported; dictionary/array characteristics and invalidation are not advertised. Uint64 values are limited to INT64_MAX by this OPACK model. Numeric metadata and values must fit the declared format. Integral range/step validation uses exact integer comparisons and modulo, including values above 2^53; floating step validation uses finite double arithmetic and a 1e-7 quotient tolerance. No long-double libm entry point is required by embedded toolchains. Values and descriptors are copied; request buffers are never retained.

Phone-owned values reject local setters. Car-owned and fixed values reject phone writes. Shared values may be written by either side, subject to the declared range, format and a pure host validation callback. Writes are requests to the host; neither success nor the post-commit callback proves physical vehicle actuation. Actual actuator permissions, feedback and safety policy belong to the host integration.

## Message handling and notifications

The processor consumes a complete decrypted Type 130 comm body with pluginID and binary OPACK pluginData. It implements configRequest/configResponse, readRequest/readResponse, writeRequest/writeResponse, registerRequest/registerResponse and updateNotify. An explicit signed integer or null transactionID is required and echoed. The plugin identifier must match the configured plugin. Malformed or duplicate identifiers reject the entire request; unknown values and refused writes use the reference's error value -6727. Hosts may explicitly register [typed service controls](vehicle-controls.md); unregistered controlRequest IDs retain the reference's unknown-command status -6735. An unknown command returns the local unsupported error without fabricating a wire response.

Read and register return known current values and per-IID unavailable errors. Registration can follow a known characteristic that has no current value, so a later valid phone write can generate its first notification. Only subscribed changes become notifications; repeated identical values do not. Changes coalesce to the latest value and are emitted on the high-priority lane. Successful serialization consumes those pending changes, and the caller must retain the resulting bytes until sent or the authenticated session ends. A failed encoding retains them. A session reset removes subscriptions and pending notifications while preserving current vehicle values. Unregister is not invented because its wire form is not established by the reviewed reference.

Requests are staged before serialization. Output exhaustion leaves values, subscriptions and write callbacks unchanged. Write-policy validation must be pure and may run before a serialization failure; the post-commit callback runs only after success. All calls have one serialized owner, and callbacks must not reenter the object. Responses use the request lane. Public status reports request/rejection, write, subscription and notification counters. Local errors distinguish invalid input, unknown plugin/IID, unsupported commands, wrong ownership and bounded workspace/output exhaustion.

## Duplex DataStream transport primitive

The internal airplay_data_stream API provides a separate authenticated duplex APTransportPackage transport. Its owner supplies independently derived Pair-Verify DataStream Output/Input keys and a peer address, and polls only ready events. One instance accepts one matching connection, including the IPv6 scope, and never accepts a replacement under the same keys. Receiver composition below now supplies fresh stream IDs, key derivation and SETUP routing. The existing iAP tunnel is unchanged.

Only complete authenticated package bodies reach the callback. Sync packages enqueue a reply with the exact eight-byte token before delivering a comm/cmnd body; replies and unknown message types do not reach the application. Transport receipt is independent of the application result. Outgoing application bodies use async/cmnd packages. Each body is limited to 65,536 bytes, and the copied FIFO has at most eight packages and 131,072 total plaintext bytes. Application sends reserve one package and 32 bytes for a transport reply. Caller-visible queue exhaustion leaves an application enqueue unchanged. A peer burst that exhausts reply capacity terminates the stream visibly rather than dropping replies. No wire timeout, retransmission policy or application sequence protocol is invented here.

Partial writes and temporary RTCP_ETIMEDOUT retain encrypted bytes and continue with the same nonce/ciphertext. A chunk is encrypted once, and a package is counted as sent only after all its ciphertext is accepted by the socket. Authentication, format, callback, socket and receive-queue failures close the stream and clear keys, queued bodies and assembly buffers. Successful enqueue is delivery ownership, not proof of phone receipt. Status reports lifecycle, terminal error, peer rejections, received/delivered/ignored/sent packages and queued sync replies. Calls have one serialized owner; the borrowed complete-body callback may queue a response but cannot poll, stop or otherwise reenter the object. Socket operations must remain bounded on the integrating port.

Host tests cover independent TCP/cipher/package fragmentation, a 65,536-byte body, every truncation of a short sync package, directional encryption, exact reply tokens, ignored replies/types, short writes and temporary send/receive timeouts, copied FIFO order and byte/package limits, reserved reply capacity and overload failure, callback rejection, malformed lengths/kinds, bad authentication tags, disconnect, IPv4 peer/IPv6 scope binding and cleanup. These are synthetic tests, not real-phone evidence.

## Receiver registration and SETUP lifecycle

The public rtcp/data_stream.h contract and Receiver configuration accept an explicit channel mask, a complete-body handler and an optional close handler. Zero registration preserves Classic behavior. The three registered transport kinds map to the Vehicle State normal/high and UI Sync UUIDs. No app protocol, enabledFeatures entry, vehicleStateProtocolInfo, uiSyncInfo or displayPanels declaration is synthesized by registration. Integrating hosts must register only handlers they implement. D213 dedicated Ultra development profiles now separately opt into an explicitly SIMULATED engine Vehicle State processor; ordinary Classic profiles remain detached. Optional Vehicle State and UI Sync application processor attachments are implemented. Neither attachment synthesizes capability declarations.

The initial phone SETUP offers are snapshotted only after successful setup. Registered channels require the corresponding vehicleStateProtocol or uiSync offer, a completed Pair-Verify, an active encrypted control connection and initial setup. Missing/invalid prerequisites are refused. Each Type 130 SETUP currently contains one stream, matching the existing iAP restriction; mixed/batched Type 130 requests are rejected before endpoints start. Separate requests may establish all three channels concurrently, with separate ports, stream IDs, keys, cipher counters, queues and state. iAP retains streamID 1; registered transports use increasing IDs above one. An identical active SETUP returns its existing endpoint; a changed seed or connection metadata cannot replace it implicitly.

The Pair-Verify secret and decimal seed derive directional HKDF-SHA512 keys with DataStream-Salt<seed> and the Input/Output labels. The shared session salt ledger spans screen, audio, iAP and registered transports. A new transport attempt reserves its salt and ID before listener creation, even when creation fails. Close, selective TEARDOWN, output-encoding failure and full TEARDOWN never release consumed salts for reuse under that pairing session. A fresh seed may reopen a retired transport with a fresh ID. Selective TEARDOWN addresses streamID; omitting streamID selects all Type 130 endpoints. Retiring one channel preserves the others and media. Full session destruction also retires listeners that never connected. Stale poll readiness and old stream IDs cannot target a replacement.

rtcp_receiver_send_data_stream copies a body into the selected connected queue and reports invalid arguments, absent connection or queue exhaustion. It is callable in the complete-body callback. rtcp_receiver_get_data_stream_status reports registration, phone offer, endpoint state/ID/port, terminal error and transport counters; closed counters persist until the next RTSP controller, while stopped receivers return idle counters with registration preserved. Close callbacks run once per owned endpoint and do not establish peer receipt. The Linux/RT-Thread poll capacity is now 25 to include the optional endpoint set; custom ports must support that capacity when enabling it.

The encrypted Host end-to-end controller independently derives stream keys and drives actual TCP sockets through both native and compatibility Receiver configurations. It checks authentication/initial-setup/phone-offer gates, malformed features, three simultaneous duplex channels, exact sync replies and callback responses, duplicate SETUP, cross-kind/media salt collisions, listener-failure salt retirement, fresh-seed reopening, stale-ID and selective/all-Type-130 teardown, bad-tag isolation and never-connected listener cleanup across controller reconnect. These exchanges use synthetic transport payloads; they do not verify real Vehicle State/UI Sync application interactions or a real iPhone.

## Vehicle State Receiver composition

Set rtcp_receiver_config_t.vehicle to a borrowed processor to install the application handler on both Vehicle State lanes. Attach a processor to one Receiver, retain it until Receiver destruction and serialize all access on the Receiver owner. A raw registration overlapping either vehicle lane is rejected; an independent raw UI Sync backend remains supported. An omitted processor preserves Classic routing and callbacks and allocates no vehicle delivery buffers. Attachment allocates approximately 48 KiB of bounded delivery buffers on the heap and does not advertise /info capabilities. Processor attachment is an explicit host policy, independent of raw transport registration.

Requests pass through authenticated Type 130 routing into config/read/write/register handlers, with responses on the request lane. One encoded response per lane may wait outside the transport queue. Queue exhaustion retains the exact response and retries during Receiver polling. If another request arrives while that lane's retained response still cannot queue, the new request is rejected before processing and the lane closes. An already committed write is not rolled back by a later connection failure; transport ACK, application response and physical actuation remain distinct. Malformed/unsupported application messages terminate that lane visibly.

Subscribed changes serialize into a retained HIGH notification. Queue exhaustion or a missing HIGH connection keeps these bytes for retry; subsequent local changes remain coalesced in the processor and follow the retained notification. Selective channel retirement drops its pending reply and increments the abandoned-reply counter, while preserving subscriptions and any unsent notification for a fresh HIGH endpoint within the same authenticated session. Authentication loss or Receiver start/stop clears subscriptions and all retained messages, preserves current vehicle values and counts abandoned buffers. Bytes already accepted by the transport queue have no application delivery guarantee and are not replayed across channel replacement.

rtcp_receiver_get_vehicle_delivery_status reports attachment, pending response/notification byte counts, copied-to-transport messages, queue retries, rejected requests, abandoned messages and the last local error. Counters persist until Receiver destruction. Direct rtcp_receiver_send_data_stream calls to attached vehicle lanes return ESTATE so the processor owns their output. Hosts update local values with rtcp_vehicle_set instead.

The dedicated encrypted Host scenario uses an independent simulated controller over real TCP and Pair-Verify/ControlCipher, with synthetic catalogue IDs. It verifies config/read/write/register, transaction echo, HIGH updateNotify after selective close/reopen, retained values and cleared subscriptions at the authentication boundary, raw UI callback coexistence, and unchanged Classic audio/video exchanges. Fault-injected application tests verify exact retained bytes and ordering, queue-full retry, rejection before a second write, abandonment counts and malformed-message failure. These are Host tests; no real iPhone Vehicle State interoperability is claimed.

## Explicit Vehicle State capability negotiation

The optional airplay_info_plist_config_t.vehicle field generates vehicleStateProtocolInfo from the actual processor's catalogue, including protocol version, plugin mapping/configuration, ownership, permissions, ranges and current initial values. The existing Classic document is unchanged when the field is null. A temporary bounded heap arena supports the extra objects without expanding the Classic RTSP stack. Strings preserve explicit lengths, embedded NUL and UTF-8 through UTF-16 encoding; finite floating metadata, binary values and exact int64 integers are retained. A catalogue that does not fit the existing 6,144-byte session buffer fails with zero output length; the builder never truncates or silently omits it. No synthetic instrument panel, theme inventory, HEVC or alternate screen is added.

Set rtcp_receiver_config_t.negotiate_vehicle only with the attached Vehicle State processor and a matching /info catalogue. Receiver creation compares the entire metadata value, including current initial values, with that model. It rejects missing, mismatched or duplicate metadata. Before each accepted controller, it validates the refreshed immutable /info snapshot again; failure rejects that connection. Hosts whose vehicle values can change should rebuild the document through platform.get_info_plist before each session. A static document becomes stale when the values included as initialValue change. The opt-in does not change an already active session's snapshot.

Initial SETUP adds vehicleStateProtocol to enabledFeatures only after the phone offers that protocol and the Receiver opt-in has passed validation. Repeated initial SETUP keeps the accepted offer; a new authenticated controller negotiates again. The default response remains iAPChannel/viewAreas. Registration alone, an attached UI Sync model and a raw transport callback do not enable this declaration. rtcp_data_stream_status_t.enabled records accepted initial SETUP negotiation separately from registered/offered, socket state and phone execution. Both Vehicle lanes share the protocol enablement; UI Sync has its own [experimental single-Main-Display declaration gate](ui-sync-capabilities.md); actual host rendering/assets/presentation remain required and D213 leaves that gate disabled.

Host tests check generated metadata through Python plistlib, independently re-encoded dictionary/reference layouts, float/integer/string/data fidelity, UTF-16 surrogate pairs, exact integers above 2^53, duplicate/mismatched metadata, every truncation and output exhaustion. Encrypted controller tests inspect enabledFeatures, reject an invalid refreshed snapshot, exercise a fresh controller without an offer and retain Classic media coverage. These are synthetic Host controller results, not real iPhone negotiation.

## Tests and acceptance

The SDK Host tests exercise the LIVI configRequest byte fixture, negative transaction echo, catalogue structure and permissions, absent values, registration, numeric limits and step checks, host refusal, partial per-IID write errors, copied strings, callback timing, output-failure rollback, notification retry/coalescing/reset, unknown controls, truncations and a deterministic malformed-input corpus under ASan/UBSan. Display tests cover geometry and touch mapping; metadata tests verify that defaults remain Classic and optional features are absent. These tests are not iPhone interoperability evidence.

On 2026-11-15 the original LIVI checkout at the reference revision passed cargo test --locked -p livi-cp --lib on Ubuntu 24.04/WSL with Rust/Cargo 1.100.0 and OpenSSL 3.0.13: 179 passed, zero failed/ignored/filtered. This includes 15 info, 27 Vehicle State, one broad UI Sync and four iAP tunnel tests. [Selected original output and environment](evidence/livi-cp-host-20261115.txt) preserve the test identities and scope. Source and Cargo.lock were unchanged, with build output outside the checkout. A Windows attempt could not compile livi-base's Unix file-permission API, so no reference tests ran on Windows. A later separate run passed six livi-core theme_catalog tests and one livi-ui-model layout test; see the [theme review](livi-theme-review.md) and [original output](evidence/livi-theme-host-20261115.txt). Those tests cover synthetic metadata/cache/layout behavior, not full official theme rendering. Reference Host success does not prove D213, real-phone or official Ultra acceptance.

L1 remains partial: Vehicle State and UI Sync Receiver composition now have encrypted Host coverage; Vehicle State capability composition is now explicitly gated, and an experimental single-Main-Display UI Sync gate checks bound inventory and matching metadata; actual host assets/rendering/presentation remain incomplete. The registered Type 130 transport has encrypted Host SETUP coverage, not real-phone validation. L2 fusion, L3 real-iPhone Ultra negotiation, L4 real-iPhone Vehicle State/UI Sync, L5 Type 111 and official product acceptance remain NOT_RUN for this implementation. Complete Classic regression is maintained separately by the integrating host.

## Remaining implementation

The [two-video session and experimental public Receiver transport](video-stream-session.md) now separate Type 110 and Type 111 lifecycle, listeners, keys/nonces, media sinks and statistics. Explicit opt-in enables synthetic encrypted Host reception with alternate failure isolation; defaults remain Main-only. Matching metadata/altScreen negotiation, real-iPhone reception and L5 remain unverified.

The [experimental UI Sync capability gate](ui-sync-capabilities.md) now checks attached handlers, bound inventory and matching single-Main-Display metadata. The next steps remain actual host asset/renderer/presentation integration and real-phone validation, including the metadata availability and display/plugin/vehicle relationships. The UI Sync model now copies a bounded host inventory and rejects unsupported layout/palette/component choices; binding alone emits no capabilities. [UI Sync state/ACK and Receiver composition](ui-sync.md) now have independent plistlib wire tests and encrypted application-protocol coverage, including queue exhaustion and channel isolation. The existing iAP tunnel remains unchanged and receive-only. A host may explicitly attach its Vehicle State processor to the Receiver; attachment does not emit vehicleStateProtocolInfo from /info. UI Sync assets, frame composition, HEVC support, official access and qualification remain separate requirements. A D213 build must establish actual graphics/codec capability before advertising it. Optional Type 111 must have an independent sink and must not be implied by a single-screen layout.
