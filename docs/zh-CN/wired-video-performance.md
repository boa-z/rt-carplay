# 有线视频性能：v17 基线与 v18

## 历史范围与当前集成

本文保留 v17 至 v24 的调查、实验和测试结果。下文的版本、测试数量、“当前”配置和板端反馈均指对应历史基线，不代表现行固件已重新完成同等实机验收。D213 视频 Sink、调度组合和板级回归现归属 Luban-Lite 宿主 `application/rt-thread/rtcarplay/`；参见[宿主迁移](luban-lite-migration.md)。SDK 仍负责协议和编码视频交付。历史步骤和测量数据用于后续对照，不能据此宣称当前版本的视频性能或实机显示已验证。

v17 是用户首次确认画面可见且实体触摸可用的基线，但用户报告严重卡顿。日志没有提供实测帧率；仅凭 `screen frames=120` 不能确定 FPS。当时 /info 声明 1024x600、30 FPS，因此首个目标是在持续运动场景下实现流畅的 30 FPS。定位瓶颈前，不应提高声明帧率或降低分辨率。v17 仍单独归档供比较。

## 已确认的调度限制

应用轮询循环此前在有线模式下无条件睡眠 10 ms，再调用 airplay_rtsp_server_poll(..., 0)。Screen Server 每次就绪通知后最多执行一次阻塞 socket recv：消息头与消息体至少需要两次轮询，消息体分片时还需要更多轮询。因此，无论数据是否已经到达，该睡眠都为普通帧引入至少 20 ms 的软件节拍，并为每个额外分片再增加 10 ms。这是明确的吞吐量／延迟限制，不是完整板端流水线的测量结果。

v18 在没有前置睡眠的情况下以 10 ms 就绪超时调用 Server poll。数据可读时立即返回；空闲时由超时限制触摸队列延迟，避免忙循环。无线／mDNS 路径保留原有策略。Socket Reader 每次就绪轮询仍只执行一次 recv，不会无条件执行第二次阻塞 recv。

解码线程优先级从 20 调整为 14，高于优先级为 15 的 Receiver，防止移除睡眠后持续可读的 socket 饿死消费者。TCP/IP 保持优先级 10，系统 USB Worker 不变。解码器等待 VE/vsync 时阻塞，因此接收可与这些等待重叠。这一调度选择仍需在持续运动和触摸条件下进行板端验证。

## 已解码帧积压

Sink 此前显示每张可用的已解码图片，并在每次显示后等待 vsync，因此追赶积压时仍按面板节奏重放旧画面。v18 最多取出八张已经解码的图片，归还被更新画面替代的显示引用，只显示最新一张。旧扫描输出引用一直保留到新图层的 vsync 等待完成之后。MPP 的 Frame Manager 独立持有解码器引用；归还显示引用不会使仍在使用的 H.264 参考图片失效。

压缩 NAL 仍按顺序提交。输入 FIFO 保持有界；原有队列满时丢包会被报告，计数增长时仍需处理。本修改不声称能够修复已经损坏的压缩参考链。已解码帧跳过单独报告为 `skipped`。

## 测量方法

画面开始显示后执行一次以下命令，然后在同一视图持续拖动／滚动约 10 秒后再执行一次：

```
carplay_status
carplay_video status
```

使用第二个区间进行比较。首个区间包含启动、配对和建连时间；静态内容低于 30 FPS 可能是正常现象。

* `carplay screen RX`：已接受帧数、累计线上 KiB 和成功 recv 次数，以及自上次状态命令以来的帧率。Receiver 在其 Owner 线程中每 100 ms 采样计数器，并发布受互斥锁保护的快照；Shell 不会解引用正在使用的 Server 对象。
* `screen process_us avg/max`：Screen 消息处理的墙钟时间，包括认证／解密、Annex-B 转换、回调及调度抢占；不是独立测得的密码运算 CPU 时间。
* 视频 `fps`：自上次视频状态命令以来的图层显示次数。`packets` 统计该区间提交给 MPP 的包。旧 NAL 总计数也包含完整的 SPS/PPS 配置包。
* `queue_peak`、pending、dropped、errors 和 resets：FIFO 压力与故障。
* `elapsed_ms avg/max`：入队至出队的等待、非空 MPP 解码调用和显示耗时（图层 ioctl 加 vsync）。这些总计／最大值从启动起累计，分辨率为 RT-Thread 毫秒级。视频统计是诊断快照，不是跨线程事务性采样。
* `skipped`：显示前被更新画面替代的已解码图片数，与丢弃的压缩输入包不同。

Timing Endpoint 记录较大的对端偏移时，此前转换为毫秒会使有符号 int 溢出。v18 安全地输出秒及小数部分。该偏移仅用于日志，没有用于控制视频 Sink 节奏，因此旧负数值不能证明视频调度故障。

## 根据板端测量决定下一步

| 持续运动时的现象 | 下一步调查 |
| --- | --- |
| RX 接近 30 FPS、输出低、队列等待增长 | 分离 MPP 解码墙钟时间和显示／vsync 时间；检查 VE 完成等待及面板刷新。 |
| RX 低、队列短、处理墙钟时间高 | 用 CPU 时间分析 ChaCha20-Poly1305、Annex-B 扫描及复制；区分高优先级解码器抢占与密码运算开销。 |
| RX 低、队列短、处理时间低 | 检查发送端节奏、TCP 接收行为／窗口以及 IPHETH 吞吐量／USB 完成节奏。 |
| 输出帧率正常但交互仍延迟 | 测量触摸到 HID 再到接收画面的延迟和队列年龄；FPS 本身不能衡量交互延迟。 |
| 输入丢包增长 | 消除生产者／消费者瓶颈，或实现显式关键帧重同步；不要随机丢弃压缩 P 帧。 |

测量后可考虑用 NAL 存储池替换逐 NAL malloc/free、转移缓冲区所有权以减少复制、将耗时的 Screen 处理与控制／HID 轮询分离，以及调整 TCP／USB 排队。必须保持 DMA 生命周期／Cache 所有权及认证／Nonce 顺序正确。实现并测量前，不声称这些候选方案已有性能收益。应针对该基线每次只修改一个阶段。

入站 /command 和 /feedback 当时仍返回 405。重新检查的参考实现包括 DiPlay AirPlaySession.kt，以及 LIVI stack/control.rs、stack/feedback.rs，均处理这些路由。LIVI feedback 含音频流播放位置／时间戳信息；这不能证明缺失路由导致本项目的视频卡顿。实现语义前需要解码收到的 command 类型。v18 没有将这些错误替换为无条件成功响应。

## 验证

全部 49 项 Host 测试及平台边界检查通过，包括 Screen／RTSP 和 Timing 测试。实际 Sink 的 ASan/UBSan 回归通过，覆盖配置原子性、包槽位进展及已解码帧积压处理。积压模型验证三张输出只产生一次图层更新／vsync、归还两张被替代图片，并且只在 vsync 后释放旧扫描输出。完整 D213 构建通过。在下述解码器故障出现前，没有测量 v18 的设备 FPS、延迟和持续触摸行为；其性能修改尚未验证。

## V19：重复配置时保留参考链

v18 板端运行到达 Screen SETUP，收到两条 33 字节 H.264 配置消息，记录解码器重建后报告参考图片缺失（`ref_pic_list_reordering: i(-1) < 0`）及 VE 错误 80050100。后续图片继承损坏的参考状态。日志没有配置字节，因此长度相同不能证明 SPS/PPS 相同。这是解码正确性故障，导致性能比较失去意义。

源码检查确认 Sink 存在既有缺陷：一旦显示过任何帧，此后每条配置都会销毁解码器，即使 SPS/PPS 未变，随后仍不要求 IDR 就提交依赖图片。v18 的时序变化可能以不同方式暴露该路径；单凭日志无法分离是哪项性能修改使缺陷显现。

v19 在解码器 Owner 线程比较完整配置字节。相同配置被跳过，输出 `repeated configuration ignored` 诊断，保留解码器参考。改变后的配置会被缓存，重建推迟到 IDR 的首个 Slice。新解码器在 IDR 前先收到缓存的 SPS/PPS，等待期间不提交依赖 NAL。解码／提交失败也会隔离解码器，直到 IDR 允许重建。队列条目携带丢失代次，避免把丢包前后的条目混为一谈；丢包后的条目要求通过 IDR 重同步。IDR 后续 Slice 不能触发恢复：first_mb_in_slice 必须为零。Reset 释放扫描输出前会关闭显示图层并等待 vsync。

`carplay_video status` 增加 repeated_configs、waiting_idr 和 skipped_nals。被跳过的依赖 NAL 与 FIFO 丢包、已解码图片跳过分别统计。v18 的轮询、优先级、积压处理和计时保持不变，因此该构建将参考链生命周期修复隔离出来。

实际 Sink ASan/UBSan 测试新增覆盖：输出过帧后重复配置再跟 Inter 图片、改变配置后跟 Inter/IDR、解码错误后跟 Inter/IDR，以及输入缺口后先收到后续 IDR Slice 再收到完整 IDR 起始。一个小型参考依赖 MPP 模型会在参考被销毁后拒绝 Inter 图片。它不模拟 VE、不验证真实 SPS，也不能证明已解码帧积压处理在芯片上正确。全部 49 项应用测试和边界检查通过。D213 v19 镜像需要板端验证。

恢复当时等待发送端 IDR，不会主动请求 IDR，也不承诺恢复期限。如果 waiting_idr 持续为一且画面冻结，应保存该状态，再重连一次建立新视频流。如果没有配置重建却仍出现参考缺失错误，应调查原始码流／参考标记，并独立禁用输出合并。不能把恢复保护视为初始故障已经修复的证明。

板端检查：重复通常的启动／配对／iap2 步骤，保留启动配置、IDR 和 Reset 日志，确认画面及触摸。在持续滚动时，间隔约十秒执行两次 carplay_status 和 carplay_video status。预期是没有参考错误级联、相同的第二次配置不增加 resets、IDR 后 waiting_idr 清零，且没有持续丢包／错误。比较第二个区间的 RX FPS、显示 FPS 及排队／解码／显示耗时，再决定下一项性能修改。

## V19 板端结果与 V20 交互 TCP 实验

v19 板端接收并显示 78 张图片（含配置共 79 个 MPP 包），输入丢包、解码错误、Reset、跳过输出和等待 IDR NAL 均为零。HID 写入 70/70 成功，触摸队列未满。该次只收到一条配置，因此验证了一次正常运行，但没有在设备上触发重复配置恢复。用户仍报告流畅度很差。

RX 在 38.813 秒区间报告 2.0 FPS，首次显示报告则覆盖 88.062 秒，给出 0.8 FPS。这些区间起点不同，并包含启动／静态时间，均不是纯运动帧率，不能相除推断吞吐量比值。快照时 FIFO 为空（峰值九），排队平均 16 ms、最大 136 ms，解码 9/15 ms，显示 8/16 ms。Screen 处理平均 1.429 ms、最大 12 ms（含回调／调度抢占）。这些值没有显示持续解码积压，也不能排除瞬时停顿或输入／网络延迟。发送端节奏、TCP 延迟及纯运动帧率仍未测量。

v20 只进行一项行为实验：在 RT-Thread TCP 监听、已接受和出站 socket 上启用 TCP_NODELAY，包括 Event／HID 和 RTSP。Event Channel 发送小型加密 HID 消息，此前启用 Nagle；后续小写入可能等待未确认段的 ACK。禁用 Nagle 可去除该本地发送延迟，但不会禁用远端 Nagle、改变接收端延迟 ACK 策略，也不能证明这就是所报告的卡顿。每个 socket 只记录一次配置成功／失败，不逐报告输出。该实验不改变解码、接收轮询、显示及 USB 算法。

carplay_status 新增的累计诊断：

* receive gap：相邻完整、已接受 Screen 帧的间隔，不含首帧；包含静态时段以及流／网络／调度延迟。
* sender gap：相邻帧发送时间戳在发送端时钟域的正差值；零／倒退差值不计。时间戳精度／含义由发送端决定；这不是实测延迟，也不会跨 Host 相减时钟。
* assembly：从首批消息头字节到完整消息体、Screen 处理之前的时间；包含分组到达间隙及调度，不含第一批消息头字节到达前的等待。
* receive-gap 分桶：<=40 ms、(40,100] ms、>100 ms。均为累计计数，应比较持续运动前后的两次状态快照。

POST /command 当时开始解析并记录有界 binary-plist 类型，每会话前八条命令均记录，此后每第 64 条记录，并清理控制字符。不支持的命令保留 405，不会把未实现的 UI／音频操作报告为成功。DiPlay 处理 requestUI/duckAudio/unduckAudio，但 v19 日志只有请求长度。判断这些错误与卡顿的关系前，需要观察实际类型。Feedback 行为不变。

验证：全部 49 项 Host 测试和边界检查通过。真实 Screen Server socket 测试使用独立接收和发送时钟，在 ASan/UBSan 下验证三类间隔分桶及延迟消息头／消息体组装。实际 RT-Thread TCP Seam 还通过 SAL 头文件适配，针对 Host BSD socket 编译：IPv4/IPv6 阻塞／有界／已接受 socket 经 getsockopt 确认 NODELAY=1，并传输数据。这验证 socket 策略，不验证 lwIP 时序或性能收益。完整 D213 构建通过。测试日志位于 /tmp/ipheth-reference，文件名包含 v20。

板端比较：刷入 v20，验证 tcp_nodelay=enabled 以及画面／触摸。执行 carplay_status 和 carplay_video status，在同一视图持续拖动／滚动十秒，然后立即再次执行两条命令。保留启动时 unsupported_command type 日志及完整的第二次状态。如果 HID 手感更快但帧节奏仍低，说明本地 TCP 发送实验仅处理部分问题。发送／接收间隔相近时应调查源节奏或上游流控；发送间隔短、接收间隔成突发时应调查交付／调度；组装间隔大时需要 TCP／USB Trace。任一观察本身都不能确定根因。

## 补充 v20 视频快照

用户随后报告 187.017 秒显示 807 帧、4.3 FPS、无丢包／错误，之后 48.388 秒又显示 306 帧（6.3 FPS），仍无丢包／错误／Reset。队列峰值从九增加至十二，累计最大排队延迟从 137 增加至 192 ms；解码保持 8/15 ms，显示约 8/17 ms。这些结果显示瞬时队列压力。相应区间没有接收状态快照，也没有确认持续运动，因此源节奏与交付问题仍未区分。v21 增加的是 Demo Launcher，并未声称修复剩余性能问题；它保留 v20 TCP／间隔诊断和 v19 参考恢复。
